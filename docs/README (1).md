## Overview

This branch establishes the foundational database schema for the ITCA Student Clocking System. The system allows students to clock in and out of physical classroom sessions by scanning a time-limited QR code, with attendance records stored against their user profile and class.

## Database Architecture

### Entity Overview

The schema consists of six tables organised around three concerns: identity, session management, and attendance tracking.

```
Roles ──────────┐
                ├──► Users ──────────► Attendance ◄──── Classes ──► QRSessions
Programmes ─────┘
```

### Table Descriptions

#### `Roles`
Lookup table defining user types. Seeded with two roles: `Admin` and `Student`.

#### `Programmes`
Defines the academic programmes offered at the campus. Each programme has a name and a year level. Currently seeded with four programmes across Cyber Security and Software Development.

#### `Users`
Central identity table for all system users. Stores both students and admins. Students are linked to a `Programme`; admins have a `NULL` programme. Includes `IsActive` flag for soft-deletion.

#### `Classes`
Represents physical classrooms. Each class holds a static `QRCodeToken` (replace placeholders with real GUIDs before deployment).

#### `Attendance`
Transactional table. Every clock-in creates a record linking a `User` to a `Class` with a timestamp. Clock-out updates `ClockOutTime`. Duplicate clock-in prevention is handled at the **application layer**, not via a database constraint.

#### `QRSessions`
Manages time-limited QR session tokens generated per class. Before a clock-in is recorded, the app validates the scanned token against this table — checking `IsActive = 1` and `ExpiresAt > GETDATE()`.

## Notes & Decisions

- **No unique constraint on daily attendance** — the application layer is responsible for preventing a student from clocking in twice in one day. This keeps the DB flexible for edge cases (e.g. admin overrides).
- **Static vs dynamic QR tokens** — `Classes.QRCodeToken` is a static identifier for the room; `QRSessions.SessionToken` is the rotating, expirable token for each session. Both exist to support different use cases.
- **IP address logging** — the `Attendance.IPAddress` field (up to 45 chars, supporting IPv6) is included for audit purposes and optional fraud detection at the application layer.
