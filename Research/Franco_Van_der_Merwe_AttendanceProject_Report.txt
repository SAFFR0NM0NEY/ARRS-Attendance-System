📑 Attendance Register Project – Research & Design Report
1. Project Goal
Build a digital attendance register system for campus deployment.

Ensure anti-cheat enforcement (prevent buddy punching, credential sharing, and multi-login on the same device).

Deliver sponsor-ready compliance messaging with clear architectural blueprints.

2. Constraints & Challenges
❌ No router access → Security must be enforced at the application/cloud level.

❌ No device fingerprinting / UUID-based authentication → Removed from technical approach.

❌ Packet Tracer lab simulation → Dropped from scope.

❓ Backend hosting details unclear → Must adapt recommendations for both Firebase and SQL hosting.

3. Authentication & Access Control
Daily Token Issuance

Students receive a unique token each day for attendance validation.

Tokens expire after 24 hours to prevent reuse.

Email Login + Campus Wi-Fi Restriction

Students authenticate via institutional email.

Attendance submission restricted to campus Wi-Fi IP ranges.

Admin Override & Dashboard Reporting

Admins can override attendance in special cases.

Dashboard provides real-time reporting and audit logs.

4. Anti-Cheat Strategies
Per-Student Uniqueness

Each student can only log attendance once per session.

Block multiple logins from the same device.

Session Key Lifecycle

TLS session keys used for secure communication.

Session keys rotated frequently to reduce replay attack risk.

Federated Login Options (Research Ongoing)

Exploring integration with Microsoft/Google identity providers for stronger authentication.

5. Hosting Scenarios
Firebase Hosting
Pros: Built-in authentication, scalable, mobile-first support.

Cons: Limited SQL-style relational queries.

SQL Hosting
Pros: Strong relational data handling, flexible reporting.

Cons: Requires custom authentication and token lifecycle management.

6. Security Architecture
Layered Access Control

Application-level checks (token + email).

Cloud-level restrictions (Wi-Fi IP ranges).

Admin-level overrides with audit trails.

Compliance Messaging

Sponsor-ready documentation emphasizes fairness, transparency, and anti-cheat enforcement.

Clear separation of student, admin, and backend responsibilities.

7. Next Steps
Finalize backend hosting choice (Firebase vs SQL).

Implement token lifecycle and session key rotation.

Build sponsor-ready compliance documentation with layered security diagrams.

Test anti-cheat enforcement under real-world scenarios.
