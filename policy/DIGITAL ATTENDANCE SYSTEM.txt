DIGITAL ATTENDANCE SYSTEM
SECURITY POLICY AND RED TEAM TEST PLAN

OBJECTIVE
Identify, simulate, and mitigate potential security weaknesses to ensure the attendance system is secure, auditable, and resistant to fraud or unauthorized manipulation.

1. RED TEAM TEST PLAN OVERVIEW
Scope
This test plan covers:
* QR-based attendance check-in 
* Device binding using UUID 
* IP subnet and network validation 
* Attendance cutoff rules 
* Manual overrides 
* Audit logging 
* Fraud detection and flagging 
Goal
* Prevent fraudulent attendance marking 
* Enforce access control rules 
* Ensure all suspicious actions are logged 
* Maintain integrity of attendance data under attack conditions 

2. THREAT SCENARIOS AND TEST CASES
1. Duplicate QR Scan
Test: Re-scan same QR from same or different devices
Expected: First request accepted, duplicates rejected and flagged
2. Device Spoofing
Test: Attempt check-in from unregistered device
Expected: Reject and log attempt
3. Unauthorized Network Access
Test: Attempt check-in from off-campus IP
Expected: Reject and flag
4. Attendance After Cutoff
Test: Submit after allowed time window
Expected: Mark absent and log attempt
5. Manual Override Abuse
Test: Modify record without justification
Expected: Reject or flag and log action
6. QR Replay Attack
Test: Reuse captured QR code in another session
Expected: Reject if session invalid and flag
7. Credential Abuse
Test: Login using another student’s credentials
Expected: Deny login and log attempt
8. Multiple Accounts on One Device
Test: One device used for multiple students
Expected: Flag and reject duplicate check-ins
9. API Tampering
Test: Modify request payload to bypass rules
Expected: Server rejects and logs attempt
10. Logging Evasion
Test: Attempt to bypass logging system
Expected: All actions forced into server-side logs

3. TESTING METHODOLOGY
* Controlled simulation environment only 
* Monitor logs, dashboards, and flags 
* Document results (pass/fail/partial) 
* Validate security controls against expected behavior 
* Retest after fixes 

4. EXPECTED OUTCOMES
* Unauthorized attempts are rejected 
* Suspicious behavior is flagged in real time 
* Full audit trail is maintained 
* Manual overrides require justification 
* System remains stable under abuse attempts 

5. VALIDATION EXECUTION ORDER (MANDATORY)
1. Authenticate user 
2. Authorize role 
3. Validate session and QR window 
4. Validate IP subnet 
5. Validate device UUID 
6. Check duplicate attendance 
7. Store attendance record 
8. Write audit log and flags 

6. CORE SECURITY POLICIES

6.1 Access Control Policy
* Role-based access: Student, Teacher, Admin 
* Principle of least privilege enforced 
* Secure authentication required for all users 

6.2 Attendance Data Policy
* Database is the system of record 
* All changes are logged (user, timestamp, reason) 
* Access restricted by role 

6.3 Device and Network Policy
* One device per student enforced via UUID 
* Attendance only allowed on approved school Wi-Fi 
* Device sharing is prohibited 
* Multiple devices are flagged 

6.4 Device UUID Policy (FIXED LIFECYCLE)
Generation
* UUID is created on first valid login or first attendance attempt 
Storage
* Stored in: 
o HttpOnly secure cookie 
o Database linked to student 
Validation
* UUID must match student record on every request 
* Invalid or missing UUID is rejected or flagged 
Rules
* One active UUID per student 
* New UUID creation = device change attempt (flagged) 
* Reset allowed only via admin action 
Purpose
* Prevent device spoofing 
* Enforce one-device-per-student rule 
* Support fraud detection 

6.5 QR CODE POLICY (FIXED)
* System uses a single static QR code per venue 
* QR does NOT contain session logic 
* Server validates: 
o time window 
o session validity 
* QR alone cannot grant attendance 

6.6 AUDIT & LOGGING POLICY
* All actions are logged (attendance, failures, overrides) 
* Logs are append-only (no edits or deletion) 
* Access restricted to authorized roles 

6.7 FRAUD PREVENTION POLICY
* Duplicate submissions blocked 
* Invalid devices rejected 
* Off-network attempts flagged 
* Rule-based anomaly detection enabled 

6.8 MANUAL OVERRIDE POLICY
* Only authorized staff allowed 
* Reason is mandatory 
* All overrides are logged and auditable 

6.9 RED TEAM TESTING POLICY
* Controlled environment only 
* Includes: 
o spoofing 
o QR replay 
o API manipulation 
o multi-account abuse 
* Results reported to development team 

6.10 SECURITY REVIEW POLICY
* Continuous monitoring of logs and flagged events 
* Regular updates to security rules 
* System evolves based on threat findings 

7. TERMS AND CONDITIONS
User Responsibility
* Credentials are personal and must not be shared 
* Users are responsible for all actions on their account 

Device Usage
* One device per student enforced via UUID 
* Device sharing is prohibited 
* Violations are flagged 

Network Usage
* Attendance only allowed on school Wi-Fi 
* Off-network attempts are rejected 

Attendance Integrity
* Must reflect real physical presence 
* Fraud is misconduct 

Prohibited Activities
Users may not:
* Bypass security controls 
* Share QR codes 
* Manipulate attendance data 
* Interfere with logging systems 

Monitoring
* All actions are logged and monitored 

Manual Overrides
* Restricted to authorized staff 
* Must include justification 

Disciplinary Action
* Violations may result in suspension or disciplinary measures 

SYSTEM SUMMARY
The system is designed to be:
* Secure 
* Auditable 
* Consistent 
* Enforceable 
* Resistant to fraud and abuse
